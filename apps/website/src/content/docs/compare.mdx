This page puts `color-map` next to six other color libraries. Every number below is read from a data file that a script writes, and every feature cell links to the page it comes from. Nothing here is typed by hand, so a rerun updates it.

Measured on {data.generatedAt} with color-map {v['color-map']}, culori {v.culori}, colorjs.io {v['colorjs.io']}, chroma-js {v['chroma-js']}, @texel/color {v['@texel/color']}, lightningcss {v.lightningcss} and colord {v.colord}.

## Summary

- `color-map` is smaller than culori, colorjs.io and chroma-js for the same job, and larger than `@texel/color` and `colord`. Those two cover far less.
- `color-map` converts between spaces at roughly culori's speed (within about 15% of it, depending on the pair), and is faster at parsing, mixing and gamut mapping. It is about {times('toCss (oklch)')} times slower at `toCss` and about {times('toHex (srgb)')} times slower at `toHex`.
- colorjs.io has more color spaces and more contrast algorithms, including APCA. `color-map` has no APCA yet (issue [#255](https://github.com/cyberuni/color-map/issues/255)).
- lightningcss is a native Rust CSS tool for build time. It is not a browser library, so it has no browser size.

## Browser size

Sizes are minified and gzipped bytes of a bundle that contains only what the scenario imports. "Convert one color" parses `#3b82f6`, converts it to `oklch` and writes it back as a string. colord has no `oklch`, so its row converts to `hsl` instead, which is less work than the others do.

<CompareSizes />

Read the `color-map` rows with care:

- `parse` pulls in the whole CSS parser and every color space it can read. That is why the convert scenario costs {kb(s['color-map'].convert)} kB.
- When you do not parse strings, `createConverter` with two spaces costs {kb(s['color-map'].narrow)} kB. That is the narrow path, and it is the fairer match for `@texel/color`, which also takes numbers, not strings.
- `@texel/color` and `colord` are smaller than `color-map` but cover far less. `colord` has no `oklch`, no Display P3 and no gamut mapping in its core. Check the features table before you choose on size alone.
- Whole-package sizes are the bundle a bundler keeps when you re-export everything. For `color-map` that is `color`, `scale`, `palette` and `export` together.

The budgets that `color-map` enforces on itself are on the [Library page](/color-map/library/#size-budgets).

## Method and caveats

- **Size:** {data.method.sizeTool}. One entry file per scenario, tree-shaken named imports. The script is `{data.method.script}`. Competitor versions are pinned in the private `color-map-compare` workspace package, so they never reach `color-map`'s published dependencies.
- **Speed:** the repository's own benchmark, `pnpm --filter color-map bench`. It was written by the `color-map` authors, who chose the operations and inputs. Treat it as a guide, not a verdict.
- **Features:** read from each project's documentation and source at the version named above. A few "No" cells rest on a search of the installed source, not on a page that states the absence: culori and chroma-js color-mix and relative color, colord gamut mapping, and @texel/color contrast. A newer release can change a cell. chroma-js documents behavior in releases newer than 3.2.0, and cells say so when that matters.
- **Rerun:** run `pnpm --filter color-map build`, then `pnpm --filter color-map-compare measure`, and commit `apps/website/src/data/compare.json`.
- **Not covered:** accuracy of the results, memory use, and server-side speed of lightningcss.
